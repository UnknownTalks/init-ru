# Почему языковая модель может писать рабочий код

[К карте и материалам](../README.md)

## Проблема

Модель генерирует последовательность токенов. Почему результат иногда оказывается новой работающей программой, а не просто текстом, похожим на код?

## Связь человеческой задачи с программой

В обсуждениях люди оставляют намерение, попытки, сообщения об ошибках, решения и ограничения. Репозитории добавляют реализации и тесты; документация связывает API с поведением. Например, [вопрос 2009 года о повторах и порядке](https://stackoverflow.com/questions/480214/how-do-i-remove-duplicates-from-a-list-while-preserving-order) показывает, почему «просто взять set» не полностью описывает задачу.

Это иллюстрация вида полезных данных, а не утверждение о попадании именно этой страницы в обучение конкретной модели. Составы корпусов известны не всегда. В [The Pile](https://arxiv.org/html/2101.00027v1#S2.S8) документированы GitHub и Stack Exchange среди других источников.

## Механизм

Языковое моделирование учит связи между описанием задачи, синтаксисом и операциями. В генерации контекст ограничивает вероятные продолжения: имя функции, тип входа, требование сохранить порядок и уже выбранная конструкция влияют на следующие токены. Из повторно используемых механизмов может получиться сочетание, которого не было в обучении буквально.

Пример для списка строк, написанный для объяснения:

```python
def unique(xs):
    return list(dict.fromkeys(xs))
```

В Python словарь сохраняет порядок вставки, а одинаковые ключи не создают новых записей. [Документация dict](https://docs.python.org/3/library/stdtypes.html#dict). Поэтому поведение объясняется семантикой языка и выбранными операциями. Модель предлагает программу; Python исполняет её независимо от того, насколько уверенно модель её описала.

## Результат и границы

Повторяемость алгоритмов и API помогает переносу. Запоминание фрагментов тоже возможно; оно не объясняет все случаи генерации и не исключается одним новым именем функции. Успех на короткой знакомой задаче не гарантирует успеха на новом API, больших зависимостях или сложной спецификации.

Важное свойство кода — внешний сигнал исполнения. Тесты могут различать несколько текстуально разных реализаций одного поведения. В исторической [работе Codex 2021 года](https://arxiv.org/abs/2107.03374) функциональную корректность измеряли на HumanEval: pass@1 и pass@100 относятся к разным бюджетам попыток. [AlphaCode 2022 года](https://deepmind.google/blog/competitive-programming-with-alphacode/) также исследовал генерацию множества кандидатов с фильтрацией. Эти результаты не являются показателем надёжности сегодняшних агентов в произвольном проекте.

## Почему не раньше

Генерация программ и тестирование существовали раньше LLM. Изменилось сочетание методов представления, масштабов данных, архитектур и вычислений. Модель стала более гибким способом предлагать кандидатов по языковому описанию, а исполнение — способом получить проверяемую обратную связь.
